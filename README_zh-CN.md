# 📊 RepoVote 引擎

**由您的 Git 仓库驱动的去中心化决策机制**

欢迎来到 **RepoVote Engine**——这是一个革命性的开源平台，它通过将投票流程直接嵌入您的 GitHub 仓库，重新定义了社区做出集体决策的方式。与传统需要独立身份验证机制的投票工具不同，RepoVote Engine 利用了您现有的 Git 基础设施：每一项投票都是一份存储在仓库中的结构化 CSV 文件，每一次提交都等同于一次投票，而每一份合并请求则可能触发重新计票。

请将您的代码仓库视为一本鲜活的治理账本，而不仅仅是一个代码库。RepoVote Engine 将静态的版本控制转变为动态的决策引擎，让贡献者们能够使用他们早已熟悉的工具——Git 命令、拉取请求以及分支保护机制——来参与投票。这并非又一个普通的投票插件，而是一种理念上的转变：**您的代码，您的规则，您的民主**。

## 🌟 RepoVote Engine 诞生的原因

## 🌟 RepoVote Engine 为何而生

现代协作工具存在三大致命缺陷：**身份分散**（需在另一款应用中登录）、**历史不可见**（投票截止后记录便消失无踪），以及**集中式控制**（平台所有者可篡改投票结果）。RepoVote Engine通过将每一次投票都与不可变的 Git 对象绑定，彻底解决了这三大问题。

当开发者进行投票时，他们会在指定的分支中创建一个提交——该提交的哈希值即为时间戳，GPG签名则为投票者编号，而与投票相关 CSV 文件的差异内容则代表他们的选择。无需数据库、无需会话 Cookie、也无需复杂的后端系统。你的 Git 历史记录本身就是审计轨迹。

该仓库包含了用于处理这些基于 CSV 的投票、根据 GitHub 的 OAuth 权限范围验证投票者资格，并将已通过审核的结果自动合并到标准 `votes/main` 分支中的运行时程序。它设计为可作为无服务器函数、GitHub Action 或自托管的 Node.js 服务来运行。

### 📋 先决条件

在部署 RepoVote Engine 之前，请确保您的环境支持以下条件：

- 一个设置了分支保护规则的 GitHub 仓库（非必需但强烈推荐）  
- GitHub OAuth 应用凭证的访问权限（客户端 ID 和客户端密钥）  
- 用于工作进程的 Node.js 运行时环境（版本 18 LTS 或更高）  
- 能够处理带有 BOM 标记的 UTF-8 编码文件的 CSV 解析器

### ⚙️ 配置架构

RepoVote Engine 采用“配置即代码”的设计理念。所有设置均存储在项目根目录下的 `voteconfig.yml` 文件中。以下是一个最简示例：

```yaml
polls:
  - path: polls/feature-priority.csv
    voters: members
    approval_threshold: 0.6
    deadline: 2026-12-31T23:59:59Z
    anonymity: true
identity:
  provider: github
  required_org: your-org-name
  min_account_age_days: 30
output:
  results_branch: votes/consolidated
  notify_on_merge: true
```

在初始化过程中，每个参数都会根据 JSON 规范进行验证——如果配置文件中存在拼写错误，工作进程将拒绝启动，并输出包含具体行号的详细错误信息。

## 🔑 核心功能

### 🗳️ 原生 CSV 投票引擎

每个投票都是一份由您自行定义列名的简单 CSV 文件。一个典型的投票文件可能如下所示：

| 提案 | 投票者 | 选择 | 时间戳 |
|----------|-------|--------|-----------|
| 支持第三季度路线图？ | octocat | 是 | 2026-04-12T10:30:00Z |
| 支持第三季度路线图？ | torvalds | 否 | 2026-04-12T11:15:00Z |

无需使用任何专用格式或数据库模式。您可以使用任意电子表格工具编辑投票内容，通过 `git add` 将其提交，并像处理其他文件一样追踪变更。

### 🔐 基于 GitHub 的原生身份验证

RepoVote 引擎将所有的身份验证工作交由 GitHub 的 OAuth 流程处理。当投票者启动会话时，系统会将其重定向至 GitHub，要求其授权最小范围的权限（`read:user` 和 `read:org`），随后在投票者返回后，工作进程会生成一个包含其 GitHub 用户 ID、用户名以及所属组织成员状态的签名 JWT。

- **反Sybil措施**：可通过配置最低账号年龄来防止恶意批量投票  
- **组织范围权限控制**：仅允许特定GitHub组织或团队的成员参与投票  
- **每个身份仅投一票**：通过比对各投票分支的提交SHA值来实现该限制

### 📈 可追溯的审计日志

每一票都对应一次提交。提交信息遵循结构化的格式：

```
[VOTE] 投票内容：feature-priority.csv | 选项：React生态系统 | 投票者：已通过验证
```

提交历史记录中包含了已添加投票者信息的更新版 CSV 文件。通过 `git log --all polls/feature-priority.csv` 即可查看该投票的全部历史记录。任何试图篡改过往投票的恶意行为都会导致历史记录出现分支，这类异常情况能够被立即识别出来。

### 🌐 多语言界面

网页控制台会自动检测浏览器的语言偏好，并提供包括英语、西班牙语、法语、德语、日语、韩语及阿拉伯语在内的20多种语言的本地化文本。投票描述支持Unicode格式，因此提案文本可使用任何文字编码。

### 📱 响应式且无障碍的用户界面

该界面基于轻量级的网页组件架构构建，能够完美适配手机屏幕、平板电脑及桌面设备。所有交互元素均符合WCAG 2.1 AA标准——屏幕阅读器可读取投票结果，导航功能完全支持键盘操作，且配色方案会尊重用户的`prefers-color-scheme`设置。

### 🛡️ 全天候运行的工作进程可靠性

该工作进程包含一个健康检查接口，用于监控以下内容：
- 对 Git 仓库的文件系统访问情况
- GitHub API 的速率限制使用状况
- JWT 签名密钥的轮换情况
- CSV 文件的完整性（校验和验证）

一旦任何检查失败，该工作进程就会返回 HTTP 503 状态码，并将结构化的警报记录到可配置的 webhook（例如 PagerDuty 或 Slack）中。

| 场景 | RepoVote Engine 的作用 |
|------|------------------------|
| **开源项目治理** | 允许维护者通过拉取请求对 RFC 提案进行投票 |
| **社区功能优先级排序** | 用户可投票决定下一步要处理哪些问题——投票记录会透明地保存在仓库中 |
| **组织政策制定** | 将团队政策以 CSV 投票形式存储；通过 Git 追踪批准历史 |
| **学术研究知情同意** | 利用不可篡改的提交记录来留存研究的知情同意信息 |

## 🧩 架构概览

## 🧩 架构概览

```
┌─────────────────┐     ┌──────────────────────┐     ┌─────────────────┐
│  GitHub OAuth   │◄────│  RepoVote Worker     │────►│  Git Repository  │
│  (身份验证)     │     │  (无服务器/自托管)   │     │  (处理投票CSV)     │
└─────────────────┘     └──────────────────────┘     └─────────────────┘
         │                       │                            │
         ▼                       ▼                            ▼
    用户浏览器           投票处理                   审计日志（提交记录）
```

该工作节点充当中介角色：它通过 GitHub 对用户进行身份验证，核验其参与资格，将投票记录以提交的形式写入临时分支，一旦达到预设阈值，便会将这些投票合并到最终结果分支中。
